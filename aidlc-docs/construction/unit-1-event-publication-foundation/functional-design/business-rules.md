# Business Rules: Unit 1 Event Publication Foundation

## Event Emission Rules

### BR-01 Event Emission Scope

The IDP must attempt event emission for all existing auth wrapper use cases in Unit 1:

- `sign_up_email`
- `sign_in_email`
- `sign_out`
- `get_session`
- `auth_ok`
- `verify_email`
- `send_verification_email`
- `request_password_reset`
- `reset_password`
- `change_password`

### BR-02 Controlled Failure Events Only

Failed events are emitted only for controlled Better Auth error/results that are available to the use case. Unhandled thrown errors are not converted to events in Unit 1.

### BR-03 Best-Effort No-op Publishing

The initial publisher is no-op and best-effort. It must not change auth operation outcomes.

### BR-04 Stable Event Registry

Event names and allowed payload fields must be defined in a durable registry in code. Use cases should reference that registry rather than creating arbitrary event names.

## Payload Rules

### BR-05 Allowed Payload Fields

Unit 1 event payloads may include only:

- Event name.
- Outcome.
- Operation label.
- Safe reason code.
- Request ID when available.
- Internal user ID when already known and safe.
- Tenant ID when already known and safe.
- Timestamp if generated by the event service.

### BR-06 Forbidden Payload Data

Event payloads must not include:

- Passwords.
- Tokens.
- Cookies.
- Raw email addresses.
- Request bodies.
- Response bodies.
- Verification URLs.
- Reset URLs.
- Rendered email content.
- CPF.
- CNPJ.
- Phone numbers.
- Addresses.
- Domain profile data.
- Session tokens.
- Session IDs unless explicitly approved by a future audit design.
- Raw provider responses.

### BR-07 Safe Reason Codes

Reason codes must be symbolic and non-sensitive, such as `better_auth_rejected`, `invalid_request`, `not_authenticated`, or `unknown_controlled_failure`. They must not contain raw error messages, stack traces, provider details, user input, or personal data.

### BR-08 Identifier Safety

Internal user ID and tenant ID may be included only when they are already known through supported APIs and are required for future audit correlation. They must not be derived by parsing private Better Auth internals.

## Integration Rules

### BR-09 Better Auth Boundary

Use cases must continue calling Better Auth official APIs. Event publication must not reimplement credential, session, cookie, token, verification, or password reset internals.

### BR-10 Response Preservation

Event emission must not alter Better Auth response status, headers, cookies, or sanitized public payload.

### BR-11 No Persistent Side Effects

The no-op publisher must not write to a database, queue, file, external service, or log sink.

## Testing Rules

### BR-12 Invocation Tests

Tests must verify that relevant use cases call the event publisher through the interface.

### BR-13 Forbidden Data Assertion Helper

Tests must include a reusable assertion helper for forbidden keys and representative forbidden values.

### BR-14 Example-Based Tests

Unit 1 tests are example-based. PBT is not required unless implementation introduces non-trivial pure transformations.

## Security Compliance

- **SECURITY-03**: BR-06 prevents sensitive data in event payloads.
- **SECURITY-05**: BR-05 enforces payload field allowlisting.
- **SECURITY-11**: BR-04 centralizes event naming and payload rules.
- **SECURITY-12**: BR-09 preserves Better Auth boundaries.
- **SECURITY-13**: BR-04 creates a stable integrity/audit seam.
- **SECURITY-15**: BR-03 and BR-10 avoid unsafe error behavior.

## PBT Compliance

- PBT is N/A for Unit 1 as designed, provided implementation keeps event payload construction simple and allowlist-based.
- If a sanitizer with complex transformations is introduced, PBT must be added before code generation completes.
