# Web Architecture

This document explains how `apps/web` is structured today.

## Runtime

`apps/web` is a Vite React single-page application. It is not server-rendered and it is expected to consume external APIs.

The app uses:

- React for UI.
- TypeScript with strict settings.
- TanStack Router for client-side routing.
- TanStack Query for server state and cache.
- `ky` for HTTP requests.
- Tailwind CSS v4 for styling.
- shadcn/ui with Base UI primitives for reusable UI components.

## Entry Point

The browser entry point is `apps/web/src/main.tsx`.

It creates:

- The TanStack Query client.
- The TanStack Router instance.
- The React root.
- The top-level `QueryClientProvider` and `RouterProvider`.

The root route receives the Query Client through router context so future route loaders can integrate with TanStack Query.

## Routing

Routes live in `apps/web/src/routes`. Route files, URL segments, dynamic
parameter names, and search-parameter keys use English technical names.
Browser-visible labels and page copy remain in Brazilian Portuguese.
Contributor routes are grouped by owned capability, including `/processes`,
`/companies`, `/documents`, and `/notifications`. `routeTree.gen.ts` is
generated by TanStack Router and must not be manually edited.

Route generation is handled by `pnpm --filter web routes:generate` and also runs before `build` and `typecheck`.

## Modules

Application code is organized under `apps/web/src/modules`.

Current modules:

- `shared`: cross-module infrastructure and reusable primitives.
- `auth`: authentication pages, forms, components, and auth-owned assets.
- `companies`: company entities, contributor-visible registration, and the
  in-memory company collection used by the presentation.
- `processes`: canonical requests, classification, cross-profile lifecycle,
  dashboards, history, and issued-document presentation behavior.
- `documents`: contributor document collection views.
- `notifications`: contributor notification collection views.
- `operational-map`: operational map presentation behavior.
- `triage`: presentation implementation of the internal Triador Risco 2 queue, administrative process review, documents, checklist, requirements, and status transitions.

`modules/shared` contains:

- `api`: HTTP and TanStack Query infrastructure.
- `config`: environment validation and runtime configuration.
- `hooks`: shared hooks without domain ownership.
- `lib`: generic utilities.
- `lib/validators`: reusable validation and detection helpers.
- `lib/formatters`: reusable formatting and masking helpers.
- `components/ui`: shadcn/ui components and shared UI primitives.
- `components/forms`: reusable form controls built from shared UI primitives.

Business modules should expose a public API through `index.ts`. Other business modules should import from that public API instead of deep-importing internal files.

## Contributor Identity And Profiles

`modules/auth` owns the synthetic presentation identity boundary. A `User`
contains account identity, while a discriminated `Profile` contains the
persona-specific role, capabilities, and relationships. The current fixtures
provide:

- a `Contributor` profile related to `ABC Logística` and allowed to create
  processes and read its own processes and documents;
- a `Triager` profile allowed to read, review, and update triage work.

The selected fixture is persisted as a versioned `DemoSession` projection in
`sessionStorage`. Fixture passwords are used only for local credential
resolution and are never persisted. Changing profiles does not recreate the
canonical process provider, so the same synthetic request can move from the
contributor to triage, analysis, inspection, and back to the contributor.
Route guards use the profile discriminator for presentation navigation only.
The IDP and business APIs must eventually own real session validation, profile
assignment, relationships, and authorization.

## Company And Process Presentation State

`modules/companies` owns `Company`, the company registration screen, and the
runtime collection of companies linked to the contributor presentation.
`modules/processes` consumes that public API to require an explicit company
selection for each new request. A process draft never starts with a selected
company.

`modules/processes` owns a `ProcessProvider` mounted by the root route and
exported through its public API. The provider uses a reducer and exposes
separate `state`, `actions`, and derived `meta` contracts. Its versioned
presentation snapshot is persisted under `sac-nexus:process-engine:v1`. This
single browser aggregate owns the request identity, protocol, classification,
cross-profile workflow stage, public history, and issued documents. It is the
presentation substitute for a future canonical backend process record.

The provider keeps a current request, archived active request snapshots, and a
collection of completed process snapshots. Starting a request for another
company archives the current state before opening an empty draft. Selecting a
company that already owns an active request is prevented, and the contributor
can resume that request from its last phase. New drafts start with no company,
empty establishment fields, and empty questionnaire answers. Dashboards and
detail routes read snapshots by process ID so concurrent CNPJs and repeated
demonstrations do not replace earlier results.

Role-specific triage, analysis, and inspection projections use the canonical
process ID as an upsert key. Creating a projection for a later request never
removes the fixture or an earlier process, while updates replace only the
matching canonical projection.

The establishment record also owns its confirmed geographic location. The
location stores coordinates, their source, an address fingerprint, and a
confirmation timestamp. Editing CEP, street, neighborhood, or municipality
invalidates the confirmation and requires the contributor to review the pin
again. Risk classifications consume this shared establishment data; they do
not own or duplicate location state.

The provider derives an explicit `risk-1` or `risk-2` classification from the
current fixture answers and owns a bounded `classification-analyzing` phase.
The shared contributor entry has four stable stages: request, establishment,
characteristics, and classification. Risco 1 then continues to declaration and
automatic issuance. Risco 2 continues through responsible data, declaration,
document metadata, simulated payment, protocol, mandatory validation,
requirements, and a post-validation branch with or without conditional
inspection. Every non-terminal phase remains an active in-memory draft and can
be resumed without allowing a new request to
overwrite it. Once a Risco 2 request is protocolled, internal capability
providers derive role-specific queue projections from the canonical process
aggregate. Their checklists and composer drafts remain capability-owned
presentation projections, while every lifecycle transition is recorded back
into the canonical process history. Completion preserves those recorded
transitions and appends only the actual completion and issuance events instead
of replacing them with a fixed demonstration timeline.

The sign-in presentation entry resolves directly to `/dashboard`. The central
Risco 1 path follows the Figma sequence from the shared entry through review,
automatic processing, document success, and process details.

Sidebar destinations resolve by collection or entity instead of redirecting
every capability to the latest process. `/processes/avcb` currently lists all
completed regularization processes, `/companies/$companyId` renders the selected company,
`/documents` lists emitted documents, and `/notifications` lists contributor
updates. Route-level adapters project in-memory process snapshots into
document and notification view models; future business APIs must own the
authoritative collections and bounded pagination.

Contributor pages share a responsive `ContributorShell` composed from the
official shadcn `sidebar-07` primitives. The shell owns global navigation,
responsive collapse behavior, the top bar, contributor identity, and
route-derived navigation states. Process pages own only their domain content.

Risk levels are classifications and documented paths through these
capabilities, not modules, folders, providers, or component namespaces. The
durable flows are documented in:

- [`docs/web/journeys/contributor-shared-risk-classification.md`](journeys/contributor-shared-risk-classification.md)
- [`docs/web/journeys/contributor-avcb-risk-one.md`](journeys/contributor-avcb-risk-one.md)
- [`docs/web/journeys/contributor-avcb-risk-two.md`](journeys/contributor-avcb-risk-two.md)

Issued documents use one vector PDF composition with print-specific semantic
tokens, administrative hierarchy, validation data, and an explicit
demonstration watermark. The canonical taxonomy is:

- Risco 1: `Declaração de Dispensa de Licenciamento do Corpo de Bombeiros
  (DDLCB)`;
- Risco 2: `AVCB` and `Atestado de Vistoria`.

The presentation intentionally avoids official seals and states that generated
files are not legally valid government documents.

Public consultation resolves every issued DDLCB, AVCB, and inspection
attestation from completed canonical process snapshots by document number,
validation hash, process number, or protocol. The result projects the matched
document kind, classification, company, establishment, issue date, and
validity instead of using a singleton certificate fixture.

## Internal Risco 2 Presentation State

`modules/triage`, `modules/analysis`, and `modules/inspections` own their
role-specific workspaces and persist versioned presentation projections. They
do not own separate process identities. A canonical Risco 2 request is
projected into each applicable queue according to its current internal
workflow stage.

The presentation login resolves the contributor and Triador identities
independently. `/triage` redirects to `/signin` unless the current
`DemoSession` has a `triager` profile. This is a presentation route guard, not
production authorization.

Auth routes should import route-level screens from `@/modules/auth`. Auth-specific composers, forms, and assets should stay internal to `modules/auth` unless there is evidence of reusable, non-auth ownership.

## HTTP And Config

Environment variables are validated in `src/modules/shared/config/env.ts`.

The app should import the exported `env` object instead of reading `import.meta.env` directly.

The HTTP client is defined in `src/modules/shared/api/http-client.ts`. It uses `ky` and sends credentials by default, preparing the app for cookie/session based auth.

## UI

shadcn/ui is configured through `apps/web/components.json`.

The shadcn aliases point to:

- UI components: `src/modules/shared/components/ui`.
- Utilities: `src/modules/shared/lib/utils.ts`.
- Hooks: `src/modules/shared/hooks`.

Current shared UI components live under `src/modules/shared/components/ui` and are implemented with Base UI and local shadcn conventions.

## Path Aliases

The `@/*` alias points to `src/*`.

Vite uses native `resolve.tsconfigPaths` support and an explicit `@` alias in
the Vite and Vitest configuration. The explicit mapping keeps application and
test resolution consistent across tool versions.

## Monorepo Integration

The root `package.json` delegates workspace tasks to Turborepo.

Package scripts live in `apps/web/package.json`. Root scripts should remain orchestration-only and should call `turbo run <task>`.
