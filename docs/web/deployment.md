# Web Deployment

This document describes the deployment model for `apps/web`.

## Overview

`apps/web` is deployed as a Docker image published to GHCR and consumed by Dokploy through Docker Compose.

The image is environment-agnostic. Public deploy-specific configuration is provided at runtime through `/config.json`, generated by the container entrypoint from environment variables.

The Docker build stage currently uses the latest available official LTS `node:24-alpine` image because the Docker Hub `node:26-alpine` tag is not available yet. The local and GitHub Actions runtime still use `.node-version` for non-Docker checks.

The runtime stage uses the latest available stable `nginxinc/nginx-unprivileged:<version>-alpine` tag at implementation time. Keep this base image current when image scanning reports fixed high or critical vulnerabilities.

## Branch Flow

- PRs target `staging` and deploy to the shared develop environment.
- Merges to `staging` deploy the staging environment automatically.
- Merges to `main` deploy production automatically after gates pass.
- Production promotion should happen through a PR from `staging` to `main`.
- Hotfixes may target `main` only when urgent, and must be followed by a PR or cherry-pick back to `staging`.

## Merge Policy

- Protected branches use squash merge only.
- Merge commits are disabled.
- Rebase merges are disabled.
- Source branches are deleted after merge.
- Squash commit titles use the PR title.
- Squash commit messages use the PR body.

Keep PRs small so each squash commit is understandable and easy to revert.

## Branch Protection

`staging` requires these checks for web-affecting PRs:

- Pull request before merge.
- 1 approval.
- Branch up to date before merge.
- Linear history.
- `web_quality`.
- `web_security`.
- `web_deploy_develop` when web-affecting files change.
- No force pushes.
- No branch deletion.
- Rules apply to administrators.

`main` requires these checks for web-affecting PRs:

- Pull request before merge.
- 1 approval.
- Branch up to date before merge.
- Linear history.
- `web_quality`.
- `web_security`.
- No force pushes.
- No branch deletion.
- Rules apply to administrators.

## GitHub Workflows

- `.github/workflows/web-ci.yml`: PR quality/security gates for PRs targeting `main`.
- `.github/workflows/web-develop.yml`: develop image build, scan, publish, deploy, smoke check, and PR comment.
- `.github/workflows/web-staging.yml`: staging deployment and smoke check from `staging`.
- `.github/workflows/web-production.yml`: production deployment and smoke check from `main`.
- `.github/workflows/web-rollback.yml`: manual production rollback and smoke check by image digest.

Web checks use `snake_case` in the `app_stage` format:

- `web_quality`: Biome check, typecheck, Vitest coverage, and build.
- `web_security`: dependency audit.
- `web_package`: Docker build, image scan, GHCR publish, and digest resolution.
- `web_deploy_develop`, `web_deploy_staging`, and `web_deploy_production`: Dokploy deployments.
- `web_rollback_production`: manual production rollback.

## Required Repository Variables

- `WEB_DEVELOP_URL`: public develop URL. Defaults to `https://dev.hermys.io` if not configured.
- `WEB_STAGING_URL`: public staging URL.
- `WEB_PRODUCTION_URL`: public production URL.

## Required Secrets

- `DOKPLOY_WEB_DEVELOP_WEBHOOK_URL`
- `DOKPLOY_WEB_DEVELOP_WEBHOOK_TOKEN`
- `DOKPLOY_WEB_STAGING_WEBHOOK_URL`
- `DOKPLOY_WEB_STAGING_WEBHOOK_TOKEN`
- `DOKPLOY_WEB_PRODUCTION_WEBHOOK_URL`
- `DOKPLOY_WEB_PRODUCTION_WEBHOOK_TOKEN`

Webhook token secrets may be empty only if the Dokploy endpoint is otherwise protected. Prefer authenticated webhooks.

## Runtime Environment Variables

The web container reads these public environment variables and writes `/config.json`:

- `WEB_API_URL`
- `WEB_AUTH_URL`
- `WEB_APP_NAME`
- `WEB_APP_ENV`
- `WEB_ENABLE_MSW`
- `WEB_GOOGLE_MAPS_API_KEY`

These values are public in the browser. Do not use them for secrets.

`WEB_GOOGLE_MAPS_API_KEY` is optional and only enables Google Street View imagery in the operational map. Use a browser-restricted Google Maps Platform key.

## Docker Compose

The initial Compose file is `apps/web/compose.yml` and contains only the `web` service.

The stack is intentionally Compose-based from the beginning so future API, worker, database, and full-stack preview services can be added without changing the deployment model.

Dokploy owns public domain, TLS, and Traefik routing configuration. Configure the web service to route traffic to container port `8080` in the Dokploy UI instead of maintaining Traefik labels in Compose.

The first CI/CD version uses a shared Dokploy environment named `develop` and a service named `sac-nexus` at `https://dev.hermys.io`. Each PR targeting `staging` overwrites this environment with the latest successful PR build.

## Image Tags

Images are published to:

```txt
ghcr.io/<owner>/<repo>/web
```

Tag policy:

- Immutable commit tag: `<commit-sha>`.
- Develop alias: `develop`.
- Staging alias: `staging`.
- Production alias: `prod`.

Deployments and PR comments should record the immutable digest.

## Rollback

Use `.github/workflows/web-rollback.yml` with a previously published image digest.

Production rollback uses the `production` GitHub Environment and runs manually through `workflow_dispatch` with an explicit image digest input.

## Smoke Checks

Web deploy and rollback workflows call these URLs after Dokploy responds:

- `GET /config.json`
- `GET /`

Smoke checks retry for up to 120 seconds to allow Dokploy to replace the running container before failing the workflow.

## External Setup Checklist

- Configure branch protection for `staging` and `main`.
- Configure the `production` GitHub Environment with required reviewers.
- Configure repository variables for develop, staging, and production URLs.
- Configure Dokploy webhook secrets.
- Keep Dokploy Autodeploy enabled for services triggered by GitHub Actions webhooks.
- Configure Dokploy branch matching so GitHub Actions-triggered webhooks are accepted for the target environment. Staging must match `staging`; production must match `main`.
- Keep the GitHub Actions Dokploy trigger payload compatible with GitHub `push` webhooks (`X-GitHub-Event: push` and `ref: refs/heads/<branch>`), because Dokploy validates the webhook branch for Git-based sources.
- Configure GHCR pull access in Dokploy.
- Configure Dokploy routing for the web service on container port `8080`.
- Configure DNS for `dev.hermys.io`.
- Validate Dokploy webhook payloads against the actual Dokploy setup.
